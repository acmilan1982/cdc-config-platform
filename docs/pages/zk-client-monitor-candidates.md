# CDC 客户端节点监控页面 — 候选设计方案

> 任务编号：ZK_MONITOR_DESIGN_001
> 设计日期：2026-07-17
> 设计依据：ZK_MONITOR_ANALYSIS_001 / ZK_MONITOR_ANALYSIS_002 已确认结论
> 页面编号：P-008（CDC 节点状态）
> 所属模块：运行监控
> 数据来源：ZooKeeper `/bsoft-cdc/clients`
> 读写性质：只读

---

## 1. 设计背景

基于已完成的 ZooKeeper 节点分析，为「CDC 节点状态」页面提供 3 套不同的候选设计方案。该页面展示 CDC 客户端进程的实时运行状态，包括在线状态、IP、状态码、详细信息（detailInfo）和各采集任务（jobs）的进度。

本任务只生成候选方案供项目负责人选择，不直接固化为最终页面规格。

## 2. 已确认业务约束

| 约束项 | 内容 | 来源 |
|--------|------|------|
| 监控范围 | `/bsoft-cdc/clients` | 项目负责人已确认 |
| 排除项 | servers、signals 节点 | 项目负责人已确认 |
| 在线判断 | alive 临时节点存在 = 在线，不存在 = 离线 | 项目负责人已确认 |
| 页面形态 | 单页面，所有客户端 + jobs 同页展示 | 项目负责人已确认 |
| 筛选 | 第一版不提供筛选 | 项目负责人已确认 |
| 分页 | 第一版不提供分页 | 项目负责人已确认 |
| 客户端排序 | 按名称升序 | 项目负责人已确认 |
| jobs 排序 | 建议按名称升序 | 项目负责人已确认 |
| detailInfo | 完整展示，保留换行，等宽字体，支持复制 | 项目负责人已确认 |

| 弹窗/抽屉 | 不使用 | 项目负责人已确认 |

## 3. 生产规模假设

| 指标 | 值 |
|------|-----|
| 客户端数量 | 通常 5～6 个，最多不超过 10 个 |
| 每客户端 jobs 数量 | 通常 5～6 个 |
| 总 job 数量 | 通常 25～36 个，最多约 60 个 |

## 4. 可用字段清单

### 客户端级

| 字段 | ZK 来源 | 类型 | 说明 |
|------|---------|------|------|
| 客户端名称 | clients/{client} 节点名 | string | 如 hosp-006 |
| 在线状态 | alive 节点是否存在 | boolean | 在线/离线 |
| IP 地址 | ip → ip | string | 10.16.18.86:10003 |
| 状态码 | status → code | string | 直接展示 |
| 状态描述 | status → description | string | 直接展示 |
| 详细信息 | status → detailInfo | string(多行) | 完整展示 |
| 更新时间 | status → updateTime | datetime | 直接展示 |
| PID | alive → pid | string | 仅在线时有值 |
| 实例 UUID | alive → instanceId | string | 仅在线时有值 |
| 启动时间 | alive → startTime | datetime | 仅在线时有值 |
| ZK 路径 | 完整节点路径 | string | 悬浮显示 |

### job 级

| 字段 | ZK 来源 | 类型 | 说明 |
|------|---------|------|------|
| 任务名称 | jobs/{job} 节点名 | string | 如 my-19c |
| 状态码 | jobs/{job}/status → code | string | 直接展示 |
| 状态描述 | jobs/{job}/status → description | string | 直接展示 |
| SCN | jobs/{job}/scn → scn | string | 可为空 |
| SCN 更新时间 | jobs/{job}/scn → updateTime | datetime | 可为空 |
| ZK 路径 | 完整节点路径 | string | 悬浮显示 |

## 5. 方案 A：客户端卡片 + 卡片内 jobs 表格

### 方案名称

**「卡片式分组布局」**

### 页面整体结构

每个客户端渲染为一张独立卡片，卡片内从上到下依次为：状态头部 → 概要信息行 → detailInfo 区域 → jobs 表格。多张卡片纵向排列，卡片之间有明显分隔。

### 客户端级字段摆放

- 卡片头部第一行：在线状态圆点 + 客户端名称（粗体）
- 卡片头部第二行：IP 地址、status.code、状态描述、更新时间
- 卡片头部第三行：PID、启动时间（在线时显示实际值，离线时显示 `--`）

### jobs 摆放方式

- 每张卡片内部放置独立的 jobs 表格
- 表格列：名称、状态（code + description 合并列）、SCN、SCN 时间
- jobs 按名称升序排列
- jobs 为 0 时表格显示单行"(无采集任务)"

### detailInfo 摆放方式

- 卡片内独立区域，位于概要信息和 jobs 表之间
- 固定高度（约 4～6 行），超出时垂直滚动
- 等宽字体（font-family: monospace）
- 右上角「复制」按钮复制全部文本
- 保留原始换行

### 在线/离线视觉表现

- 在线：绿色实心圆点 + "在线"文字 + 卡片左侧细绿色边框
- 离线：灰色实心圆点 + "离线"文字 + 卡片左侧细灰色边框
- 不得只依赖颜色区分，必须显示文字

### 自动刷新和手工刷新区域

- 页面顶部固定工具栏
- 左侧：标题 "CDC 节点状态"
- 右侧：自动刷新下拉（10/30/60 秒）+ 最后刷新时间 + 手工刷新按钮

### 原始 ZK 路径悬浮方式

- 客户端名称旁放置 `ⓘ` 图标，鼠标悬浮显示完整 ZK 路径
- job 名称旁同样支持悬浮显示路径
- 悬浮框使用 Tooltip，延迟约 500ms 出现

### jobs 超过日常规模时的处理

- 卡片内 jobs 表格区域设置 `max-height: 300px`，超出时内部垂直滚动
- 日常 5～6 个 jobs 自然完整显示，无需滚动
- 超过约 8 个时出现滚动条

### 优点

- 客户端信息聚合度高，一眼看清单个客户端的全部状态
- 卡片边界清晰，视觉扫描效率高
- detailInfo 与客户端关联直观
- 适合运维快速定位特定客户端的问题

### 缺点

- 多客户端时页面纵向较长（5 张卡片 + 展开 detailInfo）
- 跨客户端比较 jobs 不够方便
- 卡片内容量不均匀时视觉节奏受影响（如有的客户端 jobs 多有的少）

### 适用场景

- 客户端数量少（≤10）
- 运维更关注单个客户端的完整状态
- detailInfo 内容重要且需要与客户端紧密关联

### 实现复杂度

中等。卡片布局 + 内嵌表格，Element Plus `el-card` + `el-table` 即可实现。

### 推荐等级

★★★★☆（4/5）

## 6. 方案 B：客户端主表 + 同页状态详情区 + 全部 jobs 汇总表

### 方案名称

**「上下分区布局」**

### 页面整体结构

页面从上到下分为三大区域：
1. **客户端概要表**（紧凑行，可点击选中）
2. **当前选中客户端详情区**（detailInfo 完整展示）
3. **全部 jobs 汇总表**（所有客户端的所有 jobs 合并展示）

默认选中第一个客户端（按名称升序第一个）。客户端表仅展示核心概要字段，选中行后下方详情区展示 detailInfo。jobs 汇总表始终展示全部数据。

### 客户端级字段摆放

- 客户端概要表：名称（含在线圆点）、在线状态文字、IP、code、状态描述、更新时间
- 表格紧凑排列，默认选中第一行（▶ 指示器）
- 选中行高亮，下方详情区联动更新
- PID 和启动时间放在详情区标题行，不在主表中

### jobs 摆放方式

- 全部客户端的 jobs 合并为一张大表
- 表格列：客户端、任务名称、状态码、状态描述、SCN、SCN 时间

- 某客户端无 jobs 时显示一行 "(无任务)"

### detailInfo 摆放方式

- 客户端概要表和 jobs 汇总表之间
- 固定高度区域（约 6～8 行），超出内部滚动
- 等宽字体，保留换行，支持复制
- 标题行显示客户端名称、PID、启动时间
- 切换选中客户端时详情区更新

- 与方案 A 相同：页面顶部固定工具栏

- job 名称悬浮显示：`/bsoft-cdc/clients/{client}/jobs/{job}`
- 使用 Tooltip 延迟出现

### jobs 超过日常规模时的处理

- 全部 jobs 汇总表设置 `max-height: 400px`，超出时垂直滚动
- 日常 25～36 个 jobs 正好在视野内
- 极端情况（60 个）时出现滚动条

### 优点

- 客户端概要紧凑，多客户端时页面总长度可控
- 全部 jobs 在一张表中，方便跨客户端比较
- 客户端表固定高度，不因 detailInfo 长短而变化
- 表格式布局符合运维人员习惯

### 缺点

- 客户端与 jobs 的关联不如卡片式直观
- 需要选中客户端才能看到对应的 detailInfo
- 客户端表中的概要不展示 detailInfo，排查问题时多一步选择操作
- jobs 汇总表需要额外的"客户端"列来区分归属

### 适用场景

- 客户端数量较多（接近 10 个上限）
- 运维更关注跨客户端横向比较
- jobs 是主要关注对象

### 实现复杂度

中等。上下分区 + 联动选中，需处理客户端表选中与详情区联动逻辑。

### 推荐等级

★★★☆☆（3/5）

**「信息块纵向布局」**

### 页面整体结构

### 在线/离线视觉表现

- 在线：绿色圆点 + "在线" + 区块顶部分割线为绿色
- 离线：灰色圆点 + "离线" + 区块顶部分割线为灰色
- 客户端名称在离线时不变灰，保持可读性

### 自动刷新和手工刷新区域

- 与方案 A/B 相同：页面顶部固定工具栏

### 原始 ZK 路径悬浮方式

- 每个客户端区块标题行右侧有 `[ZK路径ⓘ]` 图标，悬浮显示路径
- 每个 job 名称右侧有 `[ZK路径ⓘ]` 图标，悬浮显示路径

### jobs 超过日常规模时的处理

- jobs 区域内部 `max-height: 400px`，超出时滚动
- 日常 5～6 个自然完整展示

### 优点

- detailInfo 阅读体验最佳——与上下文紧密关联，且不受表格单元格限制
- 非表格布局让长文本（detailInfo、异常堆栈）自然展示
- 信息层级清晰：基本状态 → 详情 → 任务
- 适合异常排查场景（detailInfo 信息量大时尤其有利）

### 缺点

- 多客户端时页面纵向较长
- jobs 之间缺少表格那种对齐的即时对比感
- 跨客户端横向比较不如表格式直观
- 实现上需要自定义布局，不能用现成的表格组件

### 适用场景

- detailInfo 内容丰富（长异常堆栈）
- 运维更关注单个客户端内部的完整信息链路
- 偏好非表格、更接近日志查看器的风格

### 实现复杂度

中等偏高。自定义信息块布局而非表格，需要更多 CSS 工作。

### 推荐等级

★★★☆☆（3/5）

## 9. Agent 推荐方案

**推荐方案 A：客户端卡片 + 卡片内 jobs 表格。**

### 推荐理由

1. **客户端数量少是核心前提**：5～6 个客户端最多 10 个，卡片展开后的纵向长度在可接受范围内（约 3～5 屏）。
2. **客户端上下文完整**：每个卡片自成一体，运维排查时无需切换选中状态，所有信息直接可见。
3. **detailInfo 与客户端紧密关联**：detailInfo 在卡片内部而非独立区域，排查问题时不需要离开当前客户端的上下文。
4. **实现简单**：Element Plus 的 `el-card` + `el-table` 即可实现，代码量少，维护成本低。
5. **符合"全部信息同页展示"要求**：所有客户端、detailInfo、jobs 均在同一页面直接可见。
6. **自适应**：日常 5～6 个 jobs 时表格紧凑；jobs 多时卡片内启用滚动。

### 方案 B 不推荐原因

- 客户端概要表与 detailInfo 分离，查看 detailInfo 需要先选中客户端行。
- 额外的一步选中操作降低了运维排查效率，特别是当 detailInfo 是关键信息时。

### 方案 C 不推荐原因

- 自定义信息块布局实现成本高于标准表格组件。
- 纵向长度在 3 个方案中最长，多客户端 + 多 jobs 时页面过长。
- 标签-值对形式的信息密度低于表格。
