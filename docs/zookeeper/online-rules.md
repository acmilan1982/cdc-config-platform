# 在线状态判断规则

> 分析时间：2026-07-16 17:11 CST
> 分类：可确认依据 / 不可靠依据 / 推荐规则 / 待确认问题

## 一、关键发现

### 所有节点均为永久节点

全部 23 个节点的 `ephemeralOwner` = 0x0，不存在临时节点。

这意味着 ZK 不依赖临时节点的会话机制来判断在线状态。即使客户端断开 ZK 连接，其注册节点也不会自动删除。

### 状态信息通过节点数据体现

在线状态和运行状态通过节点数据中的字段反映，而非通过节点存在性。

## 二、可确认的在线判断依据

### 1. status.code 字段

| code | description | 在线状态推断 |
|------|-------------|-------------|
| 1001 | 系统初始化 | 在线（服务端已启动） |
| 1002 | 进程运行正常 | 在线 |
| 1101 | 增量模式运行中 | 在线（采集任务运行中） |
| 2002 | 进程已停止 | 离线（客户端主动上报停止） |

依据：code 字段由客户端/服务端进程主动写入，反映进程自身状态。

### 2. updateTime 字段

所有 JSON 数据节点均包含 `updateTime` 字段（格式：yyyy-MM-dd HH:mm:ss），由进程周期性更新。

在线判断逻辑：若 `updateTime` 在合理时间窗口内持续更新，则进程在线。

| 节点 | 最后 updateTime | 时间差（相对分析时间） | 判断 |
|------|-----------------|----------------------|------|
| hosp-006/ip | 2026-07-16 15:50:34 | ~80 分钟 | 近期活跃 |
| hosp-006/status | 2026-07-16 15:50:43 | ~80 分钟 | 近期活跃 |
| hosp-006/jobs/my-19c/status | 2026-07-16 15:58:19 | ~73 分钟 | 近期活跃 |
| hosp-006/jobs/my-19c/scn | 2026-07-16 16:00:04 | ~71 分钟 | 近期活跃 |
| hosp-002/status | 2026-07-14 14:22:34 | ~2 天 | 已停止 |

### 3. ZK stat.mtime 字段

ZK 节点的 `mtime` 随数据更新而变化，可作为辅助判断依据。

| 节点 | mtime | dataVersion |
|------|-------|-------------|
| hosp-006/status | 2026-07-16 15:50:43 | 30 |
| hosp-006/jobs/my-19c/scn | 2026-07-16 16:00:04 | 23 |
| hosp-002/status | 2026-07-14 14:22:34 | 29 |
| Server001/status | 2026-07-14 15:23:02 | 10 |

## 三、不可靠的在线判断依据

### 1. 节点是否存在

所有节点均为永久节点，节点存在不代表进程在线。hosp-002 已停止但节点仍存在。

### 2. ZK ctime

节点创建时间不反映当前状态。Server001 创建于 2026-07-14 但其 status 可能持续更新。

### 3. signals 节点

signals 节点始终为空，不能用于判断。

## 四、推荐的在线判断规则

### 规则 1：status.code 直接判断（优先）

```text
IF status.code starts with "1" THEN 在线
IF status.code starts with "2" THEN 离线/停止
```

### 规则 2：updateTime 超时判断（辅助）

```text
IF (当前时间 - updateTime) > 阈值 THEN 疑似离线
```

阈值建议由项目负责人确认（例如 5 分钟或 10 分钟）。

### 规则 3：更新时间连续性判断

```text
IF updateTime 持续变化 AND status.code starts with "1" THEN 在线
IF updateTime 长时间不变 AND status.code starts with "2" THEN 确认离线
```

## 五、特殊状态说明

### 服务端 status.code = "1001"（系统初始化）

Server001 的 status 显示"系统初始化"而非"运行正常"，updateTime 停留在 2026-07-14。

**推断**：服务端可能使用与客户端不同的状态模型。"1001" 可能表示"已初始化就绪"而非"正在初始化"。也可能是服务端确实处于初始化完成后的稳定状态，不需要频繁更新 updateTime。

**待确认**：1001 是否代表正常运行状态？服务端是否不周期性更新 status？

## 六、时间字段单位

| 字段 | 格式 | 时区 | 示例 |
|------|------|------|------|
| updateTime（节点数据） | yyyy-MM-dd HH:mm:ss | CST（推断） | "2026-07-16 16:00:04" |
| ctime（ZK stat） | EEE MMM dd HH:mm:ss zzz yyyy | CST | "Thu Jul 16 15:50:43 CST 2026" |
| mtime（ZK stat） | EEE MMM dd HH:mm:ss zzz yyyy | CST | "Thu Jul 16 16:00:04 CST 2026" |

节点数据中的时间字段为**秒级精度**（字符串格式，无毫秒部分）。
