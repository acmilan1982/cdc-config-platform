## 2. 功能背景与当前现状

- 前端已存在左侧菜单“日志查询”与路由 `/monitor/log-query`，当前页面内容为占位页（`LogQueryPage.vue`）。
- 本功能后续实现将替换该占位内容。
- 平台存在两张字段结构相同的日志表：`CDC_LOG_ERROR`（错误日志）与 `CDC_LOG_CORRECT`（正确日志），本功能面向这两张表提供统一的只读查询入口。
- 约 40 个源数据源首次全量产生的 `CDC_LOG_CORRECT` 与 `CDC_LOG_ERROR` 日志合计至少约 20 亿条（正确日志预计占主要部分）；页面、游标分页、SQL、索引和性能方案必须按该规模设计（见 LQ-SCOPE-12、LQ-DB-11）。
- 当前开发库 `CDC_LOG_CORRECT` 约 381 万行且主要为构造/测试数据，`CDC_LOG_ERROR` 样本极少，不能代表生产字段值域、分布和查询选择性（见 LQ-PERF-14）。
- 不得以开发库当前查询速度推断生产环境性能。
- 写入链路为 `sync-server -> Kafka -> sync-log -> CDC_LOG_CORRECT / CDC_LOG_ERROR`；分区转换与索引调整允许在完全离线窗口内进行（见 LQ-DB-10）。
- 当前阶段：后端接口尚未实现，`TARGET_TIME` 第一层 RANGE 分区键已确认，分区粒度与索引方案未确定，性能指标未验证。

## 4. 术语和数据对象

### 4.1 术语

| 术语 | 说明 |
|---|---|
| 源库 / 源表 | 数据同步的源端数据源与表，查询条件分别对应 `SOURCE_DATA_SOURCE_ID`、`SOURCE_TABLE_NAME`。 |
| 目标库 / 目标表 | 数据同步的目标端数据源与表，查询条件分别对应 `TARGET_DATA_SOURCE_ID`、`TARGET_TABLE_NAME`。 |
| 同步到目标库时间范围 | 针对 `TARGET_TIME` 字段的时间过滤条件，页面固定名称；为每一次列表查询的必填条件。 |
| 已生效条件 | 最近一次成功点击“查询”后，用于列表与分页的查询条件。 |
| 表单条件 | 用户当前编辑或重置后的查询控件值，可能尚未生效。 |
| 游标分页 | 基于固定排序（`TARGET_TIME DESC, CDC_LOG_ID DESC`）和上一页末行位置值进行的翻页方式，不使用深度 OFFSET。 |
| 日志详情 | 弹窗按需展示单条日志完整字段与完整 `LOG_DETAIL`。 |
| 原始消息 | 弹窗按需展示单条日志的 `RAW_MESSAGE` 原始文本。 |
| 数据源名称映射 | 把列表中的 `DATA_SOURCE_ID` 映射为数据源显示名称的过程，见 §7。 |

### 4.2 数据对象

- `CDC_LOG_ERROR`：错误日志表，错误日志 Tab 的数据源。
- `CDC_LOG_CORRECT`：正确日志表，正确日志 Tab 的数据源。
- `CDC_DATA_SOURCE`：数据源配置表，用于下拉候选与数据源名称映射。
- 日志记录唯一标识：`CDC_LOG_ID`，同时作为游标辅助字段与详情查询依据；在 Oracle 中为 `NUMBER(19,0)`，所有 JSON 请求与响应必须以字符串传输（见 LQ-PAGE-27 / 28）。
- 列表与查询条件涉及字段：`CDC_LOG_ID`、`SOURCE_DATA_SOURCE_ID`、`SOURCE_TABLE_NAME`、`TARGET_DATA_SOURCE_ID`、`TARGET_TABLE_NAME`、`INSTRUCTION_TYPE`、`LOG_DETAIL`、`OFFSET`、`SOURCE_TIME`、`KAFKA_ENQUEUE_TIME`、`TARGET_TIME`、`INSERT_TIME`。
- `RAW_MESSAGE`：仅按需加载，列表与普通日志详情不预读（见 LQ-DETAIL-28 / 32）。
- `RESULT_CODE`：功能涉及字段，详情弹窗展示结果码（见 LQ-DETAIL-21）。
- `RESULT_DETAIL`：存在于日志表结构中，但第一版不查询、不展示（见 LQ-DETAIL-27 / LQ-NONGOAL-15）；不作为列表或查询条件字段。
- 数据源表涉及字段：`DATA_SOURCE_ID`、`DATA_SOURCE_ORG`、`DATA_SOURCE_CATEGORY`、`FG_ACTIVE`。

| LQ-FILTER-63 | 用户点击某个 Tab 的“重置”时，该 Tab 的时间恢复为点击重置时所在自然日的 `00:00:00` 至 `23:59:59`。 |

| LQ-FILTER-67 | 后端必须独立执行时间必填、完整性、顺序和跨度校验，不得因前端已校验而省略。 |
| LQ-FILTER-68 | 需求只描述时间范围必填、默认自然日与闭区间/半开区间语义，不限定 Java 类、Oracle 函数或具体 Mapper 实现。 |

跨度公式合法示例（完整选择连续 7 个自然日，为合法边界值）：

```text
startTime    = 2026-08-01 00:00:00
endTime      = 2026-08-07 23:59:59
endExclusive = 2026-08-08 00:00:00

endExclusive - startTime = 7 × 24 小时
```

以下工作仍需等待约 40 个数据源完成首次全量，并取得 `TARGET_TIME` 真实分布后确定：

1. 最终一级 RANGE 分区边界和粒度。
2. 是否增加子分区，以及子分区类型、键和数量。
3. 最终索引名称、数量、列顺序、本地或全局属性。
4. 最终可执行分区与索引 DDL。
5. 生产等价规模下的最终执行计划和性能验收。

### 19.3 菜单开放和正式部署前置条件

最终分区、索引和生产等价性能验收属于日志查询菜单开放和正式投入使用的前置条件，不属于所有代码开发的前置条件。实施顺序如下：

```text
需求重新批准
-> API/UI/逻辑 SQL 设计
-> 前后端代码与功能测试
-> 菜单保持隐藏
-> 40 个数据源完成首次全量
-> 分析 TARGET_TIME 真实分布
-> 完全关闭日志表读写
-> 确定并执行最终分区与索引方案
-> 恢复 sync-log 并处理 Kafka 积压
-> 完成执行计划和性能验收
-> 开放日志查询菜单
```

菜单在最终分区、索引和性能验证完成前必须保持隐藏（见 LQ-DB-14）。

本文档为日志查询当前正式需求基线，可以进入 API、UI、逻辑 SQL、详细验收设计及业务代码开发；最终物理设计和性能验收完成前，不执行最终生产 DDL，日志查询菜单保持隐藏。
